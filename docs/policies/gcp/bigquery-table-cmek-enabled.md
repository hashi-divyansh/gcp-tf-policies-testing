# Ensure That All BigQuery Tables Are Encrypted With Customer-Managed Encryption Key (CMEK)

| Provider | Category | CIS Control (GCP v5.0.0) |
| -------- | -------- | ------------------------ |
| Google Cloud Platform | Encryption of data-at-rest | 7.2 |

## Description

This control checks that `google_bigquery_table` resources are encrypted with a customer-managed key. A new table passes when it sets `encryption_configuration.kms_key_name`, or when a `google_bigquery_dataset` with the same `dataset_id` and resolved, non-empty project in the same plan sets `default_encryption_configuration.kms_key_name`. Missing project identities are not treated as matching provider defaults, since different provider aliases can use different projects. Set the project explicitly when it cannot be resolved in the plan. Tables whose dataset cannot be matched must set their own key.

On updates, the table's planned `encryption_configuration.kms_key_name` must contain its own CMEK. As described in [Google's CMEK documentation](https://cloud.google.com/bigquery/docs/customer-managed-encryption#dataset_default_key), adding or changing a dataset default key does not encrypt existing tables. Logical views, external tables, and BigLake tables are excluded on both creation and updates because their data is not stored in BigQuery managed storage; materialized views are evaluated.

Customer-managed encryption keys (CMEK) let you control key rotation, access, and destruction in Cloud KMS, and disabling the key makes the data unreadable. Google-managed keys do not provide that control.

This rule is covered by the [bigquery-table-cmek-enabled](https://github.com/hashicorp/prewritten-terraform-policy-library/blob/main/policies/gcp/bigquery/bigquery-table-cmek-enabled.policy.hcl) policy.
